# Разработка и проверка

## Требования

Node.js 24, npm и PostgreSQL 16. Node указан в `.nvmrc` и `package.json`; зависимости зафиксированы в `package-lock.json`. Для первого запуска копии репозитория выполнить `npm ci`. Не копировать `node_modules`, `.next`, базу или файл окружения с другого компьютера.

В каноническом workspace зависимости и кэш уже вынесены во временные каталоги; это особенность текущего Mac, не часть репозитория. Там не переустанавливать существующие зависимости без необходимости.

## Локальный запуск

Использовать только отдельную локальную БД с синтетическими данными. Пример для уже работающей PostgreSQL на 54431 и созданной базы `igaming_lms`:

```sh
export LMS_MODE=local
export APP_ORIGIN=http://127.0.0.1:8787
export DATABASE_URL="postgres://$(id -un)@127.0.0.1:54431/igaming_lms"
export LMS_RUNTIME_DIR="${TMPDIR:-/tmp}/slot-design-lms-local"
npm run db:setup
npm run dev
```

Если роль БД отличается от имени пользователя ОС, задать её в `DATABASE_URL`. Пароль рабочего сервера в терминал или этот документ не вставлять. `db:setup` применяет миграции и локальный seed; его нельзя направлять в Supabase или рабочую базу. На текущем Mac локальный кластер уже есть; вспомогательный `scripts/local-db.sh` использует Homebrew по умолчанию, для иной установки нужен `LMS_PG_BIN` с каталогом PostgreSQL.

Открыть `http://127.0.0.1:8787`. Тестовые адреса: `alex@example.test`, `sam@example.test`, `expert@example.test`, `admin@example.test`. В режиме local ссылка входа показывается в интерфейсе, реальные письма не отправляются. В Supabase такого обхода входа нет.

## Автоматические проверки

```sh
npm run typecheck
npm test
npm run build
```

`typecheck` сначала генерирует типы Next.js, поэтому работает на чистой копии без прежнего `.next` и `next-env.d.ts`.

`npm test` пересоздаёт схему `lms` **только** в локальной БД `igaming_lms_test`. По умолчанию — текущий пользователь ОС, loopback:54431. Для другой локальной конфигурации задать `LMS_TEST_DATABASE_URL`; допускаются только loopback, точное имя `igaming_lms_test` и URL без дополнительных параметров. Обычный `DATABASE_URL` игнорируется, ключи Supabase/SMTP/Brevo в дочерние тесты не передаются. Роль тестовой БД должна уметь создавать тестовую БД и `lms_runtime`; это не рекомендация прав для рабочего приложения.

GitHub Actions повторяет типы, тесты и сборку на Linux с отдельной PostgreSQL 16. Секреты рабочего окружения ему не нужны. Результат каждого push смотреть в [Actions репозитория](https://github.com/1311-barik/slot-design-lms/actions); локальный Pass не подменяет результат этого прогона.

Первый [полный прогон на GitHub](https://github.com/1311-barik/slot-design-lms/actions/runs/41362955565) завершён успешно 1 ноября 2026: чистая установка `npm ci`, типы, 40 тестов и сборка. Это проверка сборки и серверных сценариев, не развёртывание LMS и не полная приёмка ТЗ.

Расширенные HTTP-тесты — отдельный прогон на изолированном сервере 8788:

```sh
QA_ORIGIN=http://localhost:8788 node --import tsx tests/qa-http.integration.ts
QA_ORIGIN=http://localhost:8788 node --import tsx tests/password.integration.ts
```

Этот сервер должен использовать отдельные QA-базу и папку файлов, `LMS_MODE=local`, `APP_ORIGIN=http://localhost:8788`. Скрипты проверяют origin, но не доказывают, какую БД использует сервер. Не направлять их на рабочие данные.

## Рабочее окружение

Параметры перечислены в `.env.example`. Настоящий файл хранить вне репозитория с правами 0600 и передавать процессу через сервис. База — Supabase PostgreSQL, вход — Supabase Auth, файлы — приватный Storage. `supabase:setup` меняет внешнее окружение: не запускать без отдельного задания и проверки целевого проекта. `npm run mail` отправляет накопленные письма — перед подключением реального провайдера разобрать тестовую очередь.

Для установки на Linux и передачи другому администратору использовать [HANDOFF](HANDOFF.md) и [SERVER-SETUP](SERVER-SETUP.md). Для миграций без seed есть `db:migrate`, для проверки runtime-настроек — `deploy:check`, для защищённого вызова PostgreSQL-клиента — `db:tool`; всем нужен явный `--project-ref`. Загружать секреты через `node --env-file=...`, как показано в SERVER-SETUP. Дальнейшие условия приёмки — в [списке запуска](RELEASE-CHECKLIST.md).
