# Передача LMS и перенос через Git

Комплект предназначен для администратора Linux-сервера. В Git находятся приложение, миграции, тесты, шаблоны конфигурации и инструкции. Зависимости и сборка создаются на новом сервере; файлов с компьютера автора для этого не требуется.

## Выбрать вариант

| Задача | Что делать | Что будет с данными |
| --- | --- | --- |
| Перенести действующую LMS на другой сервер | Получить доступ к репозиторию и существующему Supabase; пройти SERVER-SETUP, ветку A | Пользователи, курс, сдачи и файлы остаются в том же Supabase |
| Создать отдельную LMS для этого курса | Создать свой проект Supabase; пройти SERVER-SETUP, ветку B | Новая установка с программой курса и расписанием, без прежних участников и работ |
| Перенести также базу, Auth и файлы в другой Supabase | Отдельно подготовить и проверить перенос по BACKUP-RESTORE | Это отдельная миграция данных, Git её не выполняет |

Для смены только сервера приложения подходит первый вариант. Supabase остаётся внешним сервисом PostgreSQL, Auth и Storage; Vercel и Docker для запуска приложения не нужны.

## Что передаёт владелец

1. Доступ на чтение приватного [репозитория](https://github.com/1311-barik/slot-design-lms) и выбранный commit/tag с успешной проверкой Actions. Получатель с доступом может клонировать его на свой сервер. Для автономной копии в своём Git — создать приватный репозиторий и перенести историю с согласия владельца; не публиковать исходники автоматически.
2. Доступ к новому серверу с sudo, публичный адрес и контакт для сертификата. Ориентир проверенной установки — Ubuntu 24.04, 4 ГБ RAM; на сборку и несколько сохранённых версий нужно свободное место. Меньшие конфигурации не проверены.
3. Для действующей LMS — доступ администратора к панели Supabase и runtime-настройки из `.env.example` через защищённый канал. Нужны ограниченный пользователь БД `lms_backend`, публичный ключ Auth и серверный ключ Storage. Одного доступа к Git недостаточно.
4. Для изменения схемы — отдельное административное подключение по `.env.admin.example`. Его нельзя ставить в сервис приложения. При переносе без изменения версии схемы оно для запуска не требуется.
5. Почтовые настройки и проверенный зашифрованный резервный комплект с ключом отдельно, если передаётся ответственность за эксплуатацию. Пароли, ключи, архивы, персональные данные и рабочий `.env` не добавлять в Git или issue.

Доступы к GitHub, серверу, Supabase и почте независимы. Передача исходников сама по себе не меняет владельца этих сервисов. Текущий репозиторий остаётся приватным; получателям доступ выдаёт владелец.

## Порядок действий

1. Пройти [установку сервера](SERVER-SETUP.md): Node 24 → Git → окружение → Supabase → systemd → HTTPS.
2. Проверить приложение и вход на новом адресе. Для переноса действующего курса заранее согласовать окно переключения: два сервера с одной базой видят одни и те же данные.
3. В Supabase Auth добавить новый адрес возврата и сменить Site URL. В окружении LMS задать новый `APP_ORIGIN`. Новые приглашения и повторные ссылки LMS сформирует с этим адресом; старые письма могут вести на прежний сервер.
4. Остановить почтовый обработчик на старом сервере перед включением нового. Переключить DNS, если сохраняется домен; дождаться обновления DNS. Старый сервер и старый адрес возврата убрать после приёмки и завершения окна отката.
5. Сохранить commit, адрес, дату, результаты проверки и ответственного администратора. Передача завершена, когда получатель самостоятельно воспроизвёл запуск и проверил доступ.
