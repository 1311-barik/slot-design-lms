# Резервирование и восстановление при передаче

## Смена сервера приложения

При сохранении существующего Supabase данные не выгружаются на новый сервер: новая копия приложения подключается к тому же PostgreSQL/Auth/Storage. Сохранить прежний сервер до приёмки, остановить его почтовый обработчик перед включением нового. Откат приложения — выбор сохранённого release; он не откатывает данные.

## Что составляет резервный комплект

| Часть | Что сохранять | Чем проверять |
| --- | --- | --- |
| Приложение | Git commit, lockfile, миграции, версия Node | Чистая сборка, CI, `DEPLOYED_COMMIT` |
| LMS | Схема `lms`, данные, последовательности, политики, журнал миграций | Восстановление в изоляции, числа строк, права и пользовательский сценарий |
| Пользователи входа | Supabase Auth и соответствие ID профилей LMS | Вход после восстановления, совпадение идентификаторов |
| Вложения и материалы | Содержимое приватного бакета и metadata Storage, точные object keys | Количество, размер, SHA-256 каждого файла, скачивание через LMS |
| Настройки | Защищённые env, Auth URL/SMTP, политики доступа, сервисы, nginx | Проверка конфигурации и контрольный вход |

Архивы с работами, email и Auth — чувствительные данные. Хранить вне Git и web-root, шифровать, ограничить доступ. Ключ расшифровки хранить отдельно; для восстановления нужны и архив, и ключ. Секреты передавать через согласованное хранилище паролей, не в README. Хранить минимум одну копию вне сервера приложения. При переносе расписание и контроль успешности настраиваются заново; срок хранения должен назначить владелец.

На текущем размещении 2 ноября 2026 установлен локальный macOS LaunchAgent `com.slot-design-lms.backup`: ежедневный запуск в 03:15 по локальному времени Mac. `scripts/backup.mjs` через PostgreSQL 17 экспортирует схемы `lms`, `auth`, `storage`, скачивает все объекты приватного бакета, записывает SHA-256 в манифест и шифрует ZIP с AES-256-GCM. Архив расшифровывается и проходит `unzip -t` до признания успешным. Ключ `~/.config/slot-design-lms/backup-key` остаётся только на Mac. Запуск копирует зашифрованный архив на Hetzner по SSH; исходные данные и ключ на сервер не передаются. Статус — `~/.local/share/slot-design-lms/backups/status.json`, закрытые журналы рядом. Первый запуск по расписанию завершился с кодом 0, 17 объектов; локальная и серверная копии совпали по SHA-256. Mac должен быть включён и иметь сеть; оператор проверяет `lastSuccess`, `lastFailure`, свободное место и код LaunchAgent. Автоматического удаления старых копий нет до утверждения срока хранения.

Ночной запуск 3 ноября оборвался во время `pg_dump` и завершился кодом 1. Скрипт теперь ограничивает каждый экспорт четырьмя минутами и повторяет его до трёх раз при сбое соединения. Повторный запуск завершился успешно и передал новый зашифрованный архив; локальный и серверный SHA-256 совпали. Поле `databaseAttempts` в статусе показывает, понадобился ли повтор. Успех после повтора не отменяет необходимости следить за стабильностью Supabase/pooler и получать предупреждение, если ежедневный запуск окончательно не удался.

Для текущего владельца создана ежедневная проверка Codex «Проверка резервной копии LMS» в 09:00: она читает `status.json` и состояние launchd, молчит при штатной работе и сообщает об устаревшей копии, ошибке либо повторяющемся сетевом сбое. Передача проекта требует заменить личный Mac и эту проверку корпоративным контролем.

Полный пробный подъём в новом Supabase **остаётся открытым**: проверка целостности зашифрованного комплекта не доказывает, что Auth и Storage успешно восстановятся и пользователи смогут войти. Перед передачей компании настроить независимый от личного Mac план резервирования и безопасную передачу ключа ответственному администратору.

Для контрольной распаковки на компьютере с ключом запустить `node scripts/unpack-backup.mjs /путь/архив.aesgcm /новый/закрытый/каталог`. Команда не подключается к БД и не меняет рабочую LMS; она проверяет шифрование, ZIP и SHA-256 дампа и каждого объекта. 2 ноября свежий архив распакован, все 17 объектов прошли проверку, `pg_restore --list` показал 65 секций данных таблиц `lms`/`auth`/`storage`. Проверочный открытый каталог после проверки удалён. Для реального восстановления нужна отдельная среда и процедура ниже.

## Снимок LMS перед миграцией

Это дополнительная копия **только схемы LMS**, не полный экспорт Supabase. Использовать `pg_dump` версии не старее сервера (для текущего PostgreSQL 17 подходят клиенты 17/18). Проверить инструмент до установки; на Ubuntu стандартный пакет может содержать более старый клиент. Защищённый административный env задаётся отдельно по SERVER-SETUP.

Пример из корня клона на сервере; время и путь формируются без секретов. Команда не удаляет данные:

```sh
LMS_BACKUP_DIR="/var/backups/slot-design-lms/$(date -u +%Y%m%dT%H%M%SZ)"
sudo install -d -m 0700 "$LMS_BACKUP_DIR"
sudo /opt/slot-design-node/bin/node --env-file=/etc/slot-design-lms/admin.env --import tsx scripts/db-tool.ts \
  --project-ref PROJECT_REF -- pg_dump --format=custom --schema=lms --file="$LMS_BACKUP_DIR/lms.dump"
sudo chmod 0600 "$LMS_BACKUP_DIR/lms.dump"
sudo sha256sum "$LMS_BACKUP_DIR/lms.dump"
sudo pg_restore --list "$LMS_BACKUP_DIR/lms.dump" > /dev/null
```

`db-tool.ts` передаёт пароль клиенту через окружение, не argv; не запускать с трассировкой shell. Роль `postgres` нужна только администратору, не сервису LMS. Проверка списка архива доказывает читаемость, **не восстановимость**. До выноса с сервера зашифровать архив проверенным инструментом организации и сохранить checksum/версию приложения. Для согласованного снимка БД и объектов Storage остановить запись приложения и почту на время экспорта.

Для изолированного восстановления LMS требуются роли `lms_runtime`/`lms_backend` и совместимые объекты Supabase, на которые ссылается дамп; `pg_restore --clean` в рабочую БД не запускать. Сначала подготовить отдельную целевую БД, проверить зависимости и restore без ошибок, затем сравнить таблицы, права и файлы. Возврат БД в production — отдельная операция с согласованным окном работ.

## Полный перенос в другой проект Supabase

Копия PostgreSQL не заменяет перенос самих файлов Storage. Полный перенос включает Auth, Storage objects и настройки проекта; стандартная инструкция Supabase рассматривает их отдельно. Следовать актуальной [официальной процедуре backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), сохраняя project ref источника и назначения раздельно. Не исполнять команды источника против назначения и наоборот.

Для этой LMS полный перенос в новый Supabase ещё **не принят испытанием**. Выполненные ранее проверки текущего резервного комплекта: восстановлены 30 таблиц LMS и два файла, проверены числа строк и SHA-256; восстановление всех Auth/Storage в свежем Supabase остаётся открытым. Не отключать исходный проект на основании одного успешного SQL restore.

Приёмка полного переноса:

1. В изолированном проекте восстановить роли, схему и данные с сохранением UUID; перенести объекты с прежними ключами в приватный бакет. Почту оставить выключенной, старые ожидающие уведомления отдельно разобрать.
2. Сверить количество строк по таблицам, пользователей Auth и профили, назначения экспертов, состояния/версии сдач, количество объектов и SHA-256. Никаких пропущенных ошибок восстановления.
3. Настроить собственные ключи, restricted runtime-role и Auth URL; выполнить `check-deployment.ts`. Проверить вход, права, черновик, файл, сдачу → проверку → доработку и администрирование.
4. Зафиксировать длительность, потерю данных относительно снимка, результаты и план переключения. Только после приёмки переключать реальную LMS и рассматривать отключение источника.

Таким образом, перенос **сервера приложения** воспроизводится по SERVER-SETUP, а перенос всех данных между проектами Supabase требует отдельной проверенной процедуры.
